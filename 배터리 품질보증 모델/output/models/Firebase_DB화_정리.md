## 작업 중 발견한 문제 — 정상 팩을 불량으로 판정

전체 팩에 모델을 적용해 보니 **기존 설정으로는 정상 팩의 20%를 이상으로 판정**했습니다. 특히 OK 라벨이 붙은 시험 파일에서 드러났습니다.

| 파일 | 실제 라벨 | 기존 설정 AI 판정 |
|---|---|---|
| Test01_OK_chg | 정상 (이상 0%) | **69.8% 이상** |
| Test02_OK_dchg | 정상 (이상 0%) | **40.3% 이상** |

원인은 **정상 기준 데이터가 좁았던 것**입니다. 1000~1004번 팩 10개만 기준으로 썼는데, 이 팩들의 셀 전압 편차가 유난히 작았습니다.

| 팩 | 셀 전압 편차 (평균) |
|---|---|
| 1000_chg (기준) | 13.0 mV |
| 1002_chg (기준) | 13.5 mV |
| **Test01_OK_chg** | **30.1 mV** |
| Test03_OK_chg | 11.7 mV |

Test01은 정상인데도 편차가 기준 팩의 2.3배입니다. 기준이 좁으니 "정상의 정상적인 변동"까지 이상으로 본 겁니다.

### 해결 — 기준을 97개 팩으로 확대

| 설정 | 정상 팩 오탐율 | Test01 | Test02 |
|---|---|---|---|
| 기준 10팩 / 분위수 0.99 | **20.2%** | 69.8% | 40.3% |
| **기준 97팩 / 분위수 0.95** | **7.0%** | **0.0%** | **1.0%** |

기준을 넓히면 오탐이 줄지만 그만큼 둔감해지므로, 관리한계 분위수를 0.99 → 0.95로 낮춰 민감도를 되찾았습니다. 분위수는 **Test05/Test09 두 파일로만** 정했고 나머지 7개는 건드리지 않았습니다.

| 분위수 | 튜닝(05,09) F1 | 홀드아웃 7파일 F1 | 정상팩 오탐 |
|---|---|---|---|
| 0.90 | 0.868 | 0.994 | 13.5% |
| **0.95** | **0.820** | **0.986** | **7.0%** |
| 0.97 | 0.787 | 0.979 | 5.5% |
| 0.99 | 0.403 | 0.806 | 3.0% |

### 최종 판정 결과 — 시험 9개 중 8개 정답

| 파일 | 실제 | AI 판정 | AI 이상비율 | 실제 이상비율 |
|---|---|---|---|---|
| Test01_OK_chg | OK | OK | 0.0% | 0.0% |
| Test02_OK_dchg | OK | OK | 1.0% | 0.0% |
| Test03_OK_chg | OK | OK | 0.0% | 0.0% |
| Test04_OK_dchg | OK | OK | 0.7% | 0.0% |
| Test05_NG_chg | NG | NG | 30.7% | 84.9% |
| Test06_NG_chg | NG | NG | 91.1% | 100% |
| **Test07_NG_dchg** | NG | **OK** | 4.9% | 4.9% |
| Test08_NG_chg | NG | NG | 100% | 100% |
| Test09_NG_dchg | NG | NG | 100% | 100% |

Test07만 빗나갔는데, 이상비율을 **4.9%로 정확히 맞혔습니다.** 팩 단위 NG 기준선이 5%라 간발의 차로 OK가 된 것뿐입니다. 기준선을 3%로 낮추면 9/9가 되지만 정상 팩 오탐이 늘어납니다. 발표에서는 "시점 탐지는 정확했고 팩 단위 기준선의 문제"로 설명하는 편이 정확합니다.

## 팀장님 요청 항목 진행 상황

| 항목 | 상태 |
|---|---|
| 1. Firebase 세팅 / 초대 | **대기** — 서비스 계정 키 필요 |
| 2. PCA 정확도 원인 분석 | **완료** (아래 요약) |
| 3. 오류 잡기 | **완료** — 누수는 없었고, 기준 데이터 부족 문제를 찾아 수정 |
| 4. DB화 데이터 추리기 | **완료** — 371개 문서, 3.2 MB |
| 5. Firebase 업로드 | 키 받으면 즉시 실행 가능 |

### 2번 요약 — 정확도가 높았던 이유

누수나 오류가 아니라 **평가 조건이 관대했던 것**입니다.

1. **라벨이 사실상 파일 단위** — 테스트 5개 중 4개가 전 구간 단일 라벨(전체 행의 57%). 시점을 맞춘 게 아니라 파일을 맞춘 것에 가깝습니다.
2. **실질 표본이 5개** — 파일 단위 블록 부트스트랩 2,000회 결과 F1 95% 구간이 **[0.759, 1.000]**. 0.9866은 점추정일 뿐입니다.
3. **문제가 쉬움** — 임계값 2개짜리 3σ 규칙이 F1 0.9964로 오히려 더 높고, PCA 예측과 98.9% 일치합니다.
4. **평가에서 빠진 파일이 있었음** — Test01/02(정상)가 테스트셋에 없었습니다. 넣어보니 기존 설정에서 오탐이 쏟아졌습니다. 이번에 수정했습니다.

발표에는 F1 0.9866 단독이 아니라 **시험 단위 8/9 + 교차검증 F1 0.8615 + 신뢰구간**을 함께 쓰시는 편이 안전합니다.

## Firestore 구조

```
battery_meta/config                     셀 ID 176개, 관리한계, 모델 정보
battery_packs/{packId}                  팩 마스터 106개  → 드롭다운, KPI 카드
  └─ series/score                       시계열 배열      → 이상 점수 그래프
  └─ heatmap/cells                      셀 스냅샷 2종    → 셀 전압 Heatmap
battery_segments/{packId}               이상 구간 265건  → 그래프 하이라이트
battery_models/{modelId}                모델 5종 성능지표
```

### 화면 대응

| 화면 요소 | 읽을 문서 | reads |
|---|---|---|
| 팩 드롭다운 | `battery_packs` 전체 (앱 시작 시 1회) | 106 |
| KPI 카드 4개 | `battery_packs/{id}` | 1 |
| 이상 점수 그래프 | `battery_packs/{id}/series/score` | 1 |
| 셀 전압 Heatmap | `battery_packs/{id}/heatmap/cells` | 1 |
| 이상 구간 표시 | `battery_segments/{id}` | 1 |

드롭다운을 바꿀 때마다 **4 reads**입니다. `dcc.Store`에 캐싱하면 재조회는 0입니다.

### 주요 필드

`battery_packs/{packId}`

```
pack_id, pack_no, mode(충전/방전), source(train/test), grade(OK/NG)
n_rows, dv_mv, temp_dev, thr_dv_mv, thr_temp     ← KPI 카드 + 임계값
rule_verdict, ai_verdict, anomaly_ratio, max_phi  ← 판정
cell_v_min, cell_v_max, top_cells[5]              ← 셀 정보
has_label, label_anomaly_ratio                    ← 시험 파일만
```

`series/score` — 최대 1,000점으로 다운샘플 (파일당 최대 29 KB)

```
t[], t2[], spe[], phi[], pred[], label[]
ucl_t2, ucl_spe, n_total, n_points
```
