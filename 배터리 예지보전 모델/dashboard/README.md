> 대상 파일: `예지보전 대시보드 v2.dc.html` (화면 2a–2i, 교안 그래프 반영) · 이전 버전: `예지보전 대시보드.dc.html`, `예지보전 와이어프레임.dc.html`
> 담당: 유현경 · 배터리팩 레이저 용접 공정 예지보전

## 1. 목적

공정 조건별 **용접 출력(RealPower) 변화**를 분석하고 **이상 구간**을 찾아, 설비 담당자가 대시보드에서 바로 다음을 판단할 수 있게 한다.

- **언제** – 이상이 시작·종료된 시각
- **어디서** – 파일, 용접 포인트(PageNo), 공정 조건(SetPower)
- **왜** – 실제 출력과 예측 출력의 차이(잔차, 이상 점수)와 점검 사유
- **얼마나 급한지** – 긴급 / 높음 / 보통 우선순위

모든 화면은 “분석 결과를 보여주는 것”이 아니라 **“점검 행동으로 이어지게 하는 것”**을 기준으로 구성했다.

## 3. 분석 방식과 화면 구성의 연결

1. EDA 결과 RealPower는 SetPower와 상관 0.999 → **출력은 공정 조건으로 거의 결정된다.**
2. 따라서 LightGBM(huber, Feature 9개)으로 “조건에 맞는 정상 출력”을 예측하고,
3. 잔차를 PageNo별 기준으로 표준화한 **이상 점수** = \|잔차 − 중앙값(PageNo)\| ÷ scale(PageNo)를 계산해, **정상 보정 데이터의 99.9 백분위(3.66)를 넘으면 이상**으로 판정한다. 위험비 = 점수 ÷ 3.66 (0.8 미만 정상 · 0.8–1.0 관찰 · 1.0 이상 이상).
4. 이상 행을 시간·포인트 기준으로 묶어 **이상 구간 25개**를 만들고 우선순위를 매긴다.

> 임계값은 학습 데이터 뒤 30%(정상 보정)로만 정했다. 테스트 라벨은 평가에만 쓴다.

대시보드의 탭 순서도 이 흐름을 그대로 따른다: `데이터 탐색(근거) → 출력 예측(예측) → 이상 탐지(판정) → 점검 관리(행동)`. 다만 설비 담당자가 가장 먼저 봐야 하는 것은 “지금 점검할 것”이므로 **현황 요약과 점검 관리를 탭 맨 앞**에 두었다.

## 4. 전체 구조

- **왼쪽 사이드바**: 통합 현황 · 공급망 예측 · 품질 보증 · 예지 보전 (팀 공통)
- **헤더 탭 (예지 보전)**: 현황 요약 · 점검 관리 · 이상 탐지 · 출력 예측 · 데이터 탐색 · 데이터 관리 · 보고서
- **공통 필터 (PDM-DSH-001)**: 파일 · 기간 · SetPower(설비 조건) · PageNo · 점검필요 여부. 변경 시 KPI·그래프·목록·표가 동시에 갱신된다.

> ‘실시간 모니터링’ 대신 ‘이상 탐지’·‘출력 예측’으로 이름을 정했다. 업로드된 CSV를 일괄 분석하는 방식이라 “실시간”은 실제 동작과 맞지 않기 때문이다.

| 흐름 | 사용자 | 경로 |

## 6. 화면별 설계 이유

### 2a 현황 요약 — PDM-DSH-001/002/003, EDA-002
**왜 만들었나**: 설비 담당자가 대시보드를 열자마자 “오늘 점검할 게 있는지”를 3초 안에 알아야 한다.

**구성 이유**
- **KPI 6개**: 총 포인트 5,226, 이상 판정 305 (5.8%), 미점검 긴급 1, 최근 이상 08-03 17:47, 정상 MAE 6.4 W, 출력 드리프트 ‘주의’(83% −22.3 W). 포인트색 면은 **‘미점검 긴급’ 한 곳에만** 써서 시선을 모았고, 클릭하면 긴급 필터가 걸린 점검 목록으로 이동한다.
- **우선 점검 대상 3건**: 언제·어디·왜·급한 정도를 한 줄에 담아 목록 화면에 가지 않고도 판단할 수 있게 했다.
- **공정 조건별 이상 판정 건수**: 38% 100 · 82% 89 · 83% 90 · 35%(학습외) 26. 04_NG 이상이 모든 조건에 고르게 걸려 있어 조건이 아니라 레이저 설비 문제임을 보여준다.
- **용접 포인트 × 사이클 이상 지도**: 02_OK c17 · 03_NG 27모듈 · 04_NG 9모듈 실제 판정 결과(predictions.csv).
- **월별 출력 변화**: −20 W 기준선을 넘는 열화 징후를 미리 보여준다. 이상이 나기 전에 점검하게 하려는 예지보전의 핵심이다.

### 2b 점검 관리 · 이상 구간 목록 — PDM-INS-001/002/003/005, ANM-003
**왜 만들었나**: 이상 판정은 행 단위(수백 건)라 그대로는 점검할 수 없다. **구간 단위로 묶고 우선순위를 매겨야** 현장에서 순서대로 처리할 수 있다.

**구성 이유**
- **우선순위 규칙**: 긴급 = 39행 이상 연속 또는 0 W 포함, 높음(동일 포인트 반복) = 같은 PageNo 단발 3회 이상, 높음 = 3행 이상 연속, 보통 = 그 외. 결과: 긴급 1 · 높음 20 · 보통 4 (총 25). 기본 정렬은 우선순위 → 시작 시간.
- **점검 사유 → 대상 부위**: 출력 저하면 광학계·렌즈·레이저 소스, 출력 과다면 출력 제어부·설정값, 0 W면 발진·게이트처럼 **설비 부위까지 제시**해 담당자가 해석하지 않아도 되게 했다.
  > ⚠ **이 원인–부위 연결은 프로젝트에서 임의로 정한 규칙이다.** 가이드북에는 출력 패턴별 원인·점검 부위가 나와 있지 않고(렌즈·광학·노화·오염·레이저 소스 등 언급 없음), 데이터에도 정비 이력이 없다. 레이저 용접 설비의 일반적인 지식(렌즈 오염·소스 노화 → 같은 설정에서 출력 감소)을 바탕으로 `lightgbm_model.py`의 `inspection_reason` 규칙으로 정했으며, 실제 원인을 확정하는 것이 아니라 **점검 후보(추정)**를 제시하는 용도다.
- **상태 드롭다운**: 미점검 / 점검중 / 조치완료 / 이상없음(오경보)을 목록에서 바로 바꿀 수 있다. 오경보 건수는 임계값 개선 자료로 쓴다.
- **이상 점수·위험비 주석**: 고장 확률이 아니라 임계값 대비 배수임을 명시했다.
- **설정-출력 불일치**(04_NG 2건: 83%인데 693 W, 38%인데 1,717 W)는 라벨은 정상이지만 데이터 수집·동기화 점검이 필요한 경우로 ‘보통’에 둔다.

### 2c 이상 구간 상세 + 점검 기록 — PDM-INS-004/005, MDL-002
**왜 만들었나**: 점검 전에 “정말 이상인지, 얼마나 벗어났는지” 근거를 확인하고, 점검 후에는 결과를 남겨야 한다.

**구성 이유**
- **구간 확대 그래프**: 선택 구간과 앞뒤 1모듈(39행)을 함께 보여준다. 정상 허용 범위는 회색 띠, 이상 구간은 연한 포인트색 면으로 표시해 벗어난 정도가 한눈에 보인다.
- **같은 PageNo 과거 추이**: 03_NG의 PageNo 14처럼 **같은 포인트에서 반복되는 이상**인지 판단하는 데 쓴다.
- **구간 요약 + 점검 사유**: 평균 실제 676.9 W · 예측 1,292.3 W · PageNo 기준 1,313.3 W, 최대 점수 199.0(위험비 54.4), 이상 273행, 모듈 판정 7개 불량 의심.
- 예측은 직전 출력(PreviousPower)을 따라가므로(0 W 뒤 예측 1,588 W) PageNo 기준선을 함께 보여준다.
- **점검 기록 폼**: 상태·담당자·메모·일시를 저장(inspection_log.csv)하면 KPI가 바로 갱신된다.
- **이전/다음 구간**: 목록으로 돌아가지 않고 연속으로 점검할 수 있다.

### 2d 이상 탐지 · 분류 결과 — PDM-ANM-001/002/003/004
**왜 만들었나**: 설계서 필수 기능 ‘고장 확률·분류 결과’와 ‘혼동행렬 또는 지표’를 충족하고, 임계값이 적절한지 검증해야 한다.

**구성 이유**
- **임계값 슬라이더 (정상 보정 분위수 99.0–99.99%, 10단계)**: threshold_sweep.csv 값. 기본 99.9% = 3.66. 적용하면 KPI·점검 목록·혼동행렬이 함께 다시 계산된다.
- **지표 6개**: Accuracy 0.9975 · Precision 0.9574 · **Recall 1.0000** · F1 0.9782 · 오경보율 0.0026 · 이벤트 탐지 20/20. 불량을 놓치는 비용이 가장 크므로 Recall을 강조했다.
- 이상 점수 시계열은 X축이 실제 시간이 아니고(파일별 날짜가 다름) 이상 지도(2a)·점검 목록(2b)·실제 vs 예측(2e)과 내용이 겹쳐 제외했다.
- **혼동행렬**: TN 4,921 · FP 13 · FN 0 · TP 292. FN(누락)을 포인트색 테두리로 강조했다.
- **임계값별 Precision·Recall·F1**: 99.0%(FP 96, 오경보 이벤트 85) → 99.9%(FP 13, 5) → 99.99%(FP 2, 2). Recall은 전 구간 1.0이다.
- **한 줄 요약** (혼동행렬 아래): 전체 파일 필터 기준 “단발 19/19 · 연속 1/1 탐지 · 정상 파일 오경보 1건”. 파일을 선택하면 그 파일 기준으로 바뀐다. 파일별 표는 점검 목록(2b)과 겹쳐 제외했다.
- **공정 조건별 이상 판정 산점도**: 03_NG은 35%(학습외) 한 조건에 몰림(레시피 확인), 04_NG은 모든 조건에 걸침(레이저 설비 점검).

### 2e 출력 예측 · 실제값/예측값 — PDM-MDL-002/003
**왜 만들었나**: 설계서 필수 기능 ‘실제값/예측값’, ‘MAE/RMSE/R²’, ‘기간별 결과 조회’를 충족한다. 이상 판정의 전제인 **예측 모델을 믿을 수 있는지**를 보여준다.

**구성 이유**
- **MAE · RMSE · R² 옆에 허용 기준(20 W, 60–80 W)**을 함께 두어 설비 담당자도 “좋은 값인지” 바로 판단할 수 있게 했다.
- **실제 vs 예측 그래프**: 공정 조건별로 선이 층을 이룬다. 마우스를 올리면 시각·PageNo·SetPower·잔차·이상 점수가 나온다.
- **지표 (전체 테스트 정상 행 4,934)**: MAE 6.38 W · RMSE 22.11 W · R² 0.9979. 파일별: 01_OK 5.58 · 02_OK 6.08 · 03_NG 6.51 · 04_NG 32.04 W(설정-출력 불일치 2행 때문에 기준 초과).
- 이 탭은 모두 **선택한 파일 기준**이다. 학습 모델에 고정된 Feature 중요도는 데이터 탐색(2f)으로 옮겼다.
- **정상 행만 / 전체 행 토글**: 모델 성능은 정상 행 기준으로 평가해야 이상값에 왜곡되지 않는다.
- **파일별 회귀 성능 표** (`regression_metrics.csv`, 정상 행 기준): 01_OK → 02_OK → 03_NG → 04_NG → 전체 테스트 순. **필터와 무관하게 전 파일을 고정 표시**해 비교하고, 필터에서 고른 파일의 행을 굵게 강조해 위쪽 지표 카드와 연결한다. 기준(MAE 20 W)을 넘은 04_NG 행만 포인트색으로 표시했다 (원인: 설정-출력 불일치 2행). 이상 행을 넣으면 모델 오차가 아니라 이상 크기를 재게 되므로(04_NG 전체 행 MAE 486 W) 정상 행만 쓴다.

### 2f 데이터 탐색 (EDA) — PDM-EDA-001/002/003
**왜 만들었나**: “조건별로 기준을 따로 잡고, 거기서 벗어나면 이상으로 본다”는 판단의 **근거**를 보여준다. 평가 기준 ‘데이터 품질·EDA’(15점)에 해당한다.

**구성 이유**
- **공정 조건별 출력 분포**: 38 / 82 / 83%의 출력이 뚜렷하게 나뉜다. 전체를 한 분포로 보면 정상 범위가 너무 넓어져 이상을 놓친다는 점을 보여준다.
- **조건별 통계**: 38% 52,215행 평균 687.5 W · 82% 41,772행 1,689.0 W · 83% 41,772행 1,710.7 W. min 0과 큰 std는 2022-03-18 미출력 모듈 39행을 제거하지 않았기 때문이다.
- **변수 상관관계**: RealPower–SetPower 0.999, Length 0.997, Speed 0.996, GateOnTime 0.884. 출력이 조건으로 결정된다는 사실이 회귀 + 잔차 방식을 쓰는 근거다.
- **모델이 사용한 Feature** (학습 모델 기준): gain Speed 90.8% · Length 8.9% · SetPower 0.15% → 레시피 합계 99.9%. SetPower·Speed·Length는 상관 0.998 이상인 같은 정보라 트리가 대표로 Speed를 고른 것이며, 상관관계 결과(레시피가 출력을 결정)와 같은 의미다. split 1위 PreviousPower(3,970회) → 긴 연속 이상에서 예측이 따라갈 수 있다는 한계의 근거.
- 탭 상단에 **“학습 데이터 기준 · 파일 필터와 무관”**을 표시해 필터가 걸리는 다른 탭과 구분했다.
- 월별 출력 변화(드리프트)는 모델 설계 근거가 아니라 점검 메시지라 이 탭에서 빼고 현황 요약(2a)에만 둔다.
- 기본은 학습 데이터(135,759행 · 3,481 사이클, 0 W 사이클 포함)이고, 업로드 파일로 바꿔 볼 수 있다.

### 2g 데이터 관리 · 업로드·검증 — PDM-DAT-001/002/003, MDL-001/004
**왜 만들었나**: 설계서 필수 기능 ‘CSV 업로드/검증’에 해당한다. 잘못된 데이터가 들어가면 모든 결과가 틀리므로 **순서를 강제**해야 한다.

**구성 이유**
- **4단계 진행바**: ① 업로드 → ② 검증 → ③ 전처리 → ④ 분석 실행.
- **라벨은 선택 항목**: 이상 판정은 라벨 없이도 된다. 라벨은 혼동행렬·지표를 계산할 때만 쓴다. OK/NG는 사용자가 직접 고르지 않고 라벨 파일이 있는지로 자동 판단한다.
- **검증 결과 표 = 전처리 1–5단계와 1:1 대응**

| 단계 | 검증 항목 | 실패 시 |
|---|---|---|
| 1 | 컬럼명 앞뒤 공백 제거 · 필수 9컬럼 | 오류 |
| 2 | WorkingTime → datetime (errors="raise") | 오류 · 행 번호 표시 |
| 3 | 사이클 ID 부여 (PageNo가 1로 돌아올 때) | – |
| 4 | 사이클 완전성 (39행 · PageNo 1–39 순서) | 오류로 중단 · 사이클 번호 표시 |
| 5 | 결측·중복·IQR×4, RealPower=0 사이클 | 검사만, **행 제거 안 함** |
| – | 학습에 없는 SetPower·레시피, 라벨 행 수 일치 | 경고 / 오류 |

예시(04_NG): 오류 0 · 경고 3 (RealPower=0 39행, 학습에 없는 SetPower 9행, 학습에 없는 레시피 9행) → 분석 가능. 단일값 컬럼 SetFrequency·SetDuty는 Feature에서 제외.

- **6단계(시간 순 70/30 분할)**는 업로드 파일에는 필요 없고 **재학습할 때만** 쓰므로 ‘모델 재학습’ 패널(관리자용)로 분리했다.
- **전처리 전/후 표**: 행을 지우지 않으므로 “351 → 351 (제거 0)”을 명시해 재현성 평가에 대응했다.
- 오류가 있으면 분석 버튼이 비활성화되고, 경고만 있으면 진행하되 결과에 경고 배지를 붙인다.

### 2h 데이터 관리 · 행 단위 조회 — PDM-DAT-004, ANM-003, OUT-001
**왜 만들었나**: 점검 목록(2b)은 구간 단위라, 그 근거가 된 **개별 용접 포인트 원본**을 확인할 곳이 필요하다.

**구성 이유**
- 실제·예측·|잔차|·이상 점수·위험비·점검 사유·판정(risk_level)을 한 줄에 모았다. 값은 predictions.csv 실제 행.
- 기본값을 ‘이상 행만 보기’로 해서 봐야 할 행만 먼저 보이게 했다.
- **현재 필터가 적용된 행만 CSV로 다운로드**한다(UTF-8-SIG).

### 2i 보고서 · 다운로드 — PDM-OUT-001/002/003
**왜 만들었나**: 설계서 필수 기능 ‘결과 다운로드’와 ‘보고서 요약(핵심 결론·한계·개선 제안)’, 7번 제출물(보고서 PDF·발표)에 대응한다.

**구성 이유**
- **핵심 결론 / 한계 / 개선 제안**에 최신 분석 수치가 자동으로 채워져 발표 자료에 바로 쓸 수 있다.
- **CSV 4종**(예측 결과·점검 목록·성능 지표·조건별 요약), 보고서는 Markdown/PDF로 받는다. 그래프 PNG는 각 차트의 [PNG] 버튼으로 저장한다.

## 10. 가정 · 남은 과제

- **점검 사유(원인–점검 부위 매핑)는 프로젝트에서 임의로 정한 규칙**이다. 가이드북·데이터로 검증되지 않았으므로, `inspection_log.csv`에 실제 조치 결과(원인·조치 부위)가 쌓이면 규칙을 검증·수정해야 한다.
- 모든 수치는 `outputs/lightgbm` 산출물 기준이다. 모델을 다시 돌리면 같은 CSV를 다시 읽어 갱신한다.
- 그래프 모양(잔차 히스토그램, 실제 vs 예측 선, 이상 점수 산점도의 정상 점)은 개략 표현이며, 구현 시 predictions.csv로 그린다.
- 점검 상태는 inspection_log.csv가 빈 템플릿이라 모두 ‘미점검’으로 표시했다.
- 모델·탐지 방법 비교는 대시보드에서 제외했다 (outputs/model_comparison 결과는 보고서에 기술).
- 로고는 임시로 글자로 만들었으므로 실제 로고 파일로 교체해야 한다.
- 우선순위 규칙(연속·반복 기준)은 정비·알람 이력과 대조해 검증해야 한다.
