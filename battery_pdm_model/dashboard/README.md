# BatteryFlow AI · 예지 보전 대시보드 설계 근거

> 대상 파일: `예지보전 대시보드.dc.html` (화면 2a–2i) · 이전 버전: `예지보전 와이어프레임.dc.html`
> 담당: 유현경 · 배터리팩 레이저 용접 공정 예지보전

---

## 1. 목적

공정 조건별 **용접 출력(RealPower) 변화**를 분석하고 **이상 구간**을 찾아, 설비 담당자가 대시보드에서 바로 다음을 판단할 수 있게 한다.

- **언제** – 이상이 시작·종료된 시각
- **어디서** – 파일, 용접 포인트(PageNo), 공정 조건(SetPower)
- **왜** – 실제 출력과 예측 출력의 차이(잔차, Z-score)와 점검 사유
- **얼마나 급한지** – 긴급 / 높음 / 보통 우선순위

모든 화면은 “분석 결과를 보여주는 것”이 아니라 **“점검 행동으로 이어지게 하는 것”**을 기준으로 구성했다.

## 2. 설계 근거 자료

| 자료 | 반영 내용 |

| BatteryFlow AI 기획서 최종본 | 유현경 담당 범위: 용접 공정 분석, 설비 이상 탐지, 점검 지원 |

## 3. 분석 방식과 화면 구성의 연결

1. EDA 결과 RealPower는 SetPower와 상관 1.00 → **출력은 공정 조건으로 거의 결정된다.**
2. 따라서 LightGBM으로 “조건에 맞는 정상 출력”을 예측하고,
3. 실제값과의 잔차를 Z-score로 바꿔 **|Z| ≥ 4.0이면 이상**으로 판정한다.
4. 이상 행을 시간·포인트 기준으로 묶어 **이상 구간**을 만들고 우선순위를 매긴다.

대시보드의 탭 순서도 이 흐름을 그대로 따른다: `데이터 탐색(근거) → 출력 예측(예측) → 이상 탐지(판정) → 점검 관리(행동)`. 다만 설비 담당자가 가장 먼저 봐야 하는 것은 “지금 점검할 것”이므로 **현황 요약과 점검 관리를 탭 맨 앞**에 두었다.

## 4. 전체 구조

- **왼쪽 사이드바**: 통합 현황 · 공급망 예측 · 품질 보증 · 예지 보전 (팀 공통)
- **헤더 탭 (예지 보전)**: 현황 요약 · 점검 관리 · 이상 탐지 · 출력 예측 · 데이터 탐색 · 데이터 관리 · 보고서
- **공통 필터 (PDM-DSH-001)**: 파일 · 기간 · SetPower(설비 조건) · PageNo · 점검필요 여부. 변경 시 KPI·그래프·목록·표가 동시에 갱신된다.

> ‘실시간 모니터링’ 대신 ‘이상 탐지’·‘출력 예측’으로 이름을 정했다. 업로드된 CSV를 일괄 분석하는 방식이라 “실시간”은 실제 동작과 맞지 않기 때문이다.

## 5. 사용자 흐름

| 흐름 | 사용자 | 경로 |
|---|---|---|
| A · 일일 점검 (주 흐름) | 설비 담당자 | 현황 요약(2a) → 점검 목록(2b) → 구간 상세(2c) → 점검 기록 저장 → KPI ‘미점검 긴급’ 감소 |
| B · 신규 데이터 분석 | 분석 담당자 | 업로드·검증(2g) → 분석 실행 → 전 탭 자동 갱신 → 행 단위 조회(2h) |
| C · 원인 분석·보고 | 담당자 · 발표 | 데이터 탐색(2f) → 출력 예측(2e) → 이상 탐지(2d) → 보고서(2i) |

## 6. 화면별 설계 이유

### 2a 현황 요약 — PDM-DSH-001/002/003, EDA-002
**왜 만들었나**: 설비 담당자가 대시보드를 열자마자 “오늘 점검할 게 있는지”를 3초 안에 알아야 한다.

**구성 이유**
- **KPI 6개**: 총 포인트, 이상 판정, 미점검 긴급, 최근 이상, 정상 MAE, 출력 드리프트. 포인트색 면은 **‘미점검 긴급’ 한 곳에만** 써서 시선을 모았고, 클릭하면 긴급 필터가 걸린 점검 목록으로 이동한다.
- **우선 점검 대상 3건**: 언제·어디·왜·급한 정도를 한 줄에 담아 목록 화면에 가지 않고도 판단할 수 있게 했다.
- **공정 조건별 출력 요약**: 어떤 조건에서 이상이 많은지 보여준다. 학습에 없는 SetPower(35%)는 별도 막대로 분리했다.
- **월별 출력 변화**: −20 W 기준선을 넘는 열화 징후를 미리 보여준다. 이상이 나기 전에 점검하게 하려는 예지보전의 핵심이다.

### 2b 점검 관리 · 이상 구간 목록 — PDM-INS-001/002/003/005, ANM-003
**왜 만들었나**: 이상 판정은 행 단위(수백 건)라 그대로는 점검할 수 없다. **구간 단위로 묶고 우선순위를 매겨야** 현장에서 순서대로 처리할 수 있다.

**구성 이유**
- **우선순위 규칙**: 긴급 = 39행 이상 연속 또는 0 W, 높음 = 같은 포인트에서 3회 이상 반복 또는 3행 이상 연속, 보통 = 그 외. 기본 정렬은 우선순위 → 시작 시간.
- **점검 사유 → 대상 부위**: 출력 저하면 광학계·렌즈·레이저 소스, 출력 과다면 출력 제어부·설정값, 0 W면 발진·게이트처럼 **설비 부위까지 제시**해 담당자가 해석하지 않아도 되게 했다.
- **상태 드롭다운**: 미점검 / 점검중 / 조치완료 / 이상없음(오경보)을 목록에서 바로 바꿀 수 있다. 오경보 건수는 임계값 개선 자료로 쓴다.
- **이상 점수 주석**: |Z|를 변환한 참고 점수이며 보정된 고장 확률이 아님을 명시해 오해를 막았다.

### 2c 이상 구간 상세 + 점검 기록 — PDM-INS-004/005, MDL-002
**왜 만들었나**: 점검 전에 “정말 이상인지, 얼마나 벗어났는지” 근거를 확인하고, 점검 후에는 결과를 남겨야 한다.

**구성 이유**
- **구간 확대 그래프**: 선택 구간과 앞뒤 1모듈(39행)을 함께 보여준다. 정상 허용 범위는 회색 띠, 이상 구간은 연한 포인트색 면으로 표시해 벗어난 정도가 한눈에 보인다.
- **같은 PageNo 과거 추이**: 03_NG의 PageNo 14처럼 **같은 포인트에서 반복되는 이상**인지 판단하는 데 쓴다.
- **구간 요약 + 점검 사유**: 평균 실제·예측, 최대 |Z|, 이상 행 수를 모았다.
- **점검 기록 폼**: 상태·담당자·메모·일시를 저장(inspection_log.csv)하면 KPI가 바로 갱신된다.
- **이전/다음 구간**: 목록으로 돌아가지 않고 연속으로 점검할 수 있다.

### 2d 이상 탐지 · 분류 결과 — PDM-ANM-001/002/003/004
**왜 만들었나**: 설계서 필수 기능 ‘고장 확률·분류 결과’와 ‘혼동행렬 또는 지표’를 충족하고, 임계값이 적절한지 검증해야 한다.

**구성 이유**
- **임계값 슬라이더 (2.0–8.0)**: 적용하면 KPI·점검 목록·혼동행렬이 함께 다시 계산된다. 누락과 오경보 사이의 균형을 직접 조정할 수 있다.
- **지표 5개**: 이 중 **Recall(이상 누락 방지)**을 강조했다. 예지보전에서는 불량을 놓치는 비용이 가장 크기 때문이다.
- **Z-score 시계열**: ±4.0 임계선과 초과 지점을 보여준다. 극단값(|Z| 346)에 그래프가 눌리지 않도록 ±50 제한 토글을 두었다.
- **혼동행렬**: FN(누락)을 포인트색 테두리로 강조했다.
- **임계값별 곡선 / 파일별·모델 비교**: 라벨 없는 OK 파일은 “지표 계산 불가”로 표시한다. K-Means 비교는 결과가 아직 없어 자리만 잡아두었다.

### 2e 출력 예측 · 실제값/예측값 — PDM-MDL-002/003
**왜 만들었나**: 설계서 필수 기능 ‘실제값/예측값’, ‘MAE/RMSE/R²’, ‘기간별 결과 조회’를 충족한다. 이상 판정의 전제인 **예측 모델을 믿을 수 있는지**를 보여준다.

**구성 이유**
- **MAE · RMSE · R² 옆에 허용 기준(20 W, 60–80 W)**을 함께 두어 설비 담당자도 “좋은 값인지” 바로 판단할 수 있게 했다.
- **실제 vs 예측 그래프**: 공정 조건별로 선이 층을 이룬다. 마우스를 올리면 시각·PageNo·SetPower·잔차·Z가 나온다.
- **정상 행만 / 전체 행 토글**: 모델 성능은 정상 행 기준으로 평가해야 이상값에 왜곡되지 않는다.
- **파일별 지표 표**: 시간 분할 검증 → 테스트 파일 순서로 두고, 기준을 초과한 행(04_NG)만 포인트색으로 표시했다.

### 2f 데이터 탐색 (EDA) — PDM-EDA-001/002/003
**왜 만들었나**: “조건별로 기준을 따로 잡고, 거기서 벗어나면 이상으로 본다”는 판단의 **근거**를 보여준다. 평가 기준 ‘데이터 품질·EDA’(15점)에 해당한다.

**구성 이유**
- **공정 조건별 출력 분포**: 38 / 82 / 83%의 출력이 뚜렷하게 나뉜다. 전체를 한 분포로 보면 정상 범위가 너무 넓어져 이상을 놓친다는 점을 보여준다.
- **변수 상관관계**: RealPower–SetPower 1.00. 출력이 조건으로 결정된다는 사실이 회귀 + 잔차 방식을 쓰는 근거다.
- **월별 드리프트**: 1월 대비 82·83%에서 약 −21~22 W. 이상 판정 전의 열화 징후이며, −20 W 이하일 때 레이저 소스·광학계 점검을 권고한다.
- 기본은 학습 데이터(135,759행 · 3,481 사이클, 0 W 사이클 포함)이고, 업로드 파일로 바꿔 볼 수 있다.

### 2g 데이터 관리 · 업로드·검증 — PDM-DAT-001/002/003, MDL-001/004
**왜 만들었나**: 설계서 필수 기능 ‘CSV 업로드/검증’에 해당한다. 잘못된 데이터가 들어가면 모든 결과가 틀리므로 **순서를 강제**해야 한다.

**구성 이유**
- **4단계 진행바**: ① 업로드 → ② 검증 → ③ 전처리 → ④ 분석 실행.
- **라벨은 선택 항목**: 이상 판정은 라벨 없이도 된다. 라벨은 혼동행렬·지표를 계산할 때만 쓴다. OK/NG는 사용자가 직접 고르지 않고 라벨 파일이 있는지로 자동 판단한다.
- **검증 결과 표 = 전처리 1–5단계와 1:1 대응**

| 단계 | 검증 항목 | 실패 시 |
|---|---|---|
| 1 | 컬럼명 앞뒤 공백 제거 · 필수 9컬럼 | 오류 |
| 2 | WorkingTime → datetime (errors="raise") | 오류 · 행 번호 표시 |
| 3 | 사이클 ID 부여 (PageNo가 1로 돌아올 때) | – |
| 4 | 사이클 완전성 (39행 · PageNo 1–39 순서) | 오류로 중단 · 사이클 번호 표시 |
| 5 | 결측·중복·IQR×4, RealPower=0 사이클 | 검사만, **행 제거 안 함** |
| – | SetPower 학습 범위, 라벨 행 수 일치 | 경고 / 오류 |

- **6단계(시간 순 70/30 분할)**는 업로드 파일에는 필요 없고 **재학습할 때만** 쓰므로 ‘모델 재학습’ 패널(관리자용)로 분리했다.
- **전처리 전/후 표**: 행을 지우지 않으므로 “351 → 351 (제거 0)”을 명시해 재현성 평가에 대응했다.
- 오류가 있으면 분석 버튼이 비활성화되고, 경고만 있으면 진행하되 결과에 경고 배지를 붙인다.

### 2h 데이터 관리 · 행 단위 조회 — PDM-DAT-004, ANM-003, OUT-001
**왜 만들었나**: 점검 목록(2b)은 구간 단위라, 그 근거가 된 **개별 용접 포인트 원본**을 확인할 곳이 필요하다.

**구성 이유**
- 실제·예측·잔차·Z-score·이상 점수·점검 사유를 한 줄에 모았다.
- 기본값을 ‘이상 행만 보기’로 해서 봐야 할 행만 먼저 보이게 했다.
- **현재 필터가 적용된 행만 CSV로 다운로드**한다(UTF-8-SIG).

### 2i 보고서 · 다운로드 — PDM-OUT-001/002/003
**왜 만들었나**: 설계서 필수 기능 ‘결과 다운로드’와 ‘보고서 요약(핵심 결론·한계·개선 제안)’, 7번 제출물(보고서 PDF·발표)에 대응한다.

**구성 이유**
- **핵심 결론 / 한계 / 개선 제안**에 최신 분석 수치가 자동으로 채워져 발표 자료에 바로 쓸 수 있다.
- **CSV 4종**(예측 결과·점검 목록·성능 지표·조건별 요약), 보고서는 Markdown/PDF로 받는다. 그래프 PNG는 각 차트의 [PNG] 버튼으로 저장한다.

## 8. 시각 디자인 원칙

- **팔레트**: 중립색 `#F5F5F5`(바탕) · `#76767E`(보조 텍스트·활성 메뉴) · `#0A1119`(본문·사이드바·탭바), 포인트 `#FFFFFF` · `#DDF8F5` · `#7DE3D9` · `#16C7B7` · `#13A89B`
- **포인트색은 의미가 있을 때만**: 이상·긴급·활성 탭·주요 버튼에만 쓴다. 나머지는 흑백으로 두어 이상이 눈에 띄게 했다.
- **우선순위 = 색 진하기**: 보통 `#DDF8F5` → 높음 `#7DE3D9` → 긴급 `#16C7B7`. 색을 새로 추가하지 않고 한 계열로 구분했다.
- **대비**: 청록 바탕 위의 글자는 모두 `#0A1119`로 해 읽기 쉽게 했다.
- **숫자는 고정폭 글꼴**(IBM Plex Mono), 본문은 Pretendard를 쓴다.

## 9. 가정 · 남은 과제

- K-Means 등 모델 비교 결과가 아직 없어 2d에 자리만 잡아두었다.
- 2h의 행 값은 04_NG 패턴을 보여주는 예시이며 실제 데이터로 교체해야 한다.
- 로고는 임시로 글자로 만들었으므로 실제 로고 파일로 교체해야 한다.
